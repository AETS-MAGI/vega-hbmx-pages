MI25 vs Vega64 比較ケース

MI25 vs Vega64 comparison case

同じ tinyllama 条件で、MI25 と Vega64 の ROCm 推論を比較し、差分を「GPU性能そのもの」と「実行経路・設定差」に分けて整理したケーススタディです。

A case study that compares ROCm inference on MI25 and Vega64 under the same tinyllama conditions, separating intrinsic GPU behavior from runtime-path and setup differences.

MI25 Vega64 gfx900 ROCm tinyllama
主要観測として、ROCm同士比較では Vega64 優位が継続したが、`NumThreads=16` と `keep_alive=10m` で条件を揃えると差は縮小した。さらに Vega64 内の経路比較では `eval_tps` はほぼ同等で、差の中心は `total_duration` 側のオーバーヘッドに見える。 Key observation: Vega64 stayed ahead in ROCm-vs-ROCm runs, but the gap narrowed after aligning `NumThreads=16` and `keep_alive=10m`. In Vega64-only path comparison, `eval_tps` became nearly identical, suggesting the main difference sits in `total_duration` overhead rather than token-generation core speed.
注意: このページは、特定ホスト・特定時点でのローカル観測をまとめたものです。すべての MI25/Vega64 環境へ一般化することは意図していません。 Caution: This page summarizes local observations from specific hosts at a specific time. It is not intended as a universal rule for all MI25/Vega64 deployments.

Fact / Interpretation / Open Question

Fact / Interpretation / Open Question

Fact

  • 主比較では Vega64 優位が継続し、条件を揃えるほど差は縮小した。
  • Vega64 remained ahead in the main comparison, and the gap shrank as conditions were aligned.
  • Vega64内比較では `eval_tps` ほぼ同等、`total_duration` は fork 側が一貫して長い。
  • Inside Vega64, `eval_tps` was near-parity while fork-path `total_duration` stayed consistently longer.

Interpretation

  • 「Vega64が速い」の内訳には、GPU演算差だけでなく経路と運用設定差が混ざる。
  • The observed Vega64 advantage mixes intrinsic compute behavior with runtime-path and operational differences.
  • 最適化の主戦場は `eval_tps` だけでなく `total_duration` の余剰オーバーヘッド削減。
  • A practical optimization target is reducing excess `total_duration` overhead, not only chasing `eval_tps`.

Open Question

  • MI25 側で残る約1.1x差のうち、どこまでが host / scheduler / runtime overhead か。
  • How much of the remaining ~1.1x is host, scheduler, or runtime overhead on the MI25 side.
  • 完全同一stack比較（OS/driver/packaging）で比率がどう変化するか。
  • How this ratio changes under truly identical stack conditions (OS/driver/packaging).

再現時の最小チェックリスト

Minimal reproducibility checklist

1) backend 確認: `library=ROCm` と `compute=gfx900` をログで確認
1) Backend check: verify `library=ROCm` and `compute=gfx900` in logs
2) 条件固定: `num_thread`, `keep_alive`, `num_predict` を明示
2) Fix conditions: explicitly set `num_thread`, `keep_alive`, and `num_predict`
3) 指標分離: `eval_tps` と `total_duration` を分けて読む
3) Split metrics: read `eval_tps` and `total_duration` separately
4) 最低2セット: warm後に20-run以上を複数セット
4) At least two sets: multiple 20-run warm sets
5) 実ロード先: runner の `libggml-hip.so` 実体パスを確認 5) Actual load path: verify runner `libggml-hip.so` mapped path
